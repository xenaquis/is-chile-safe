## Planning Decisions

These decisions were left open by RESEARCH.md's "Claude's Discretion" / "Open Questions" sections. They are locked here for this phase — do not re-open in execution.

1. **"Today" semantics (RESEARCH Pitfall 1 / Assumption A2):** Anchor "today" to the **newest incident's date** across the loaded `incidents` array (`Math.max` over parsed dates), not `new Date()` at build time. Rationale: this project already lost a week of freshness silently to a cron/deploy-hook gap once (`news-cron-billing-outage` memory); anchoring to data avoids a build-vs-deploy timing skew and stays deterministic given fixed input, matching the existing `freshness.mjs` validator's separate staleness-alerting philosophy (which is not being duplicated here). `windowToday` = incidents where `date === newestDate`; `window7d` = `date >= newestDate - 7d`; `window30d` = `date >= newestDate - 30d` (equals the full `current.json` set today since the pipeline's own retention is 30 days).

2. **Facet scope (RESEARCH Open Question 1):** `byFamily`/`byRegion`/`byWindow` counts are scoped to **`current.json` only** (matches both pages' "recent incidents" framing). The archive is a **separate `byMonth` dimension** — a list of `{yearMonth, count}` built by reading each `archive/YYYY-MM.json` file independently, browsable on its own, never merged into the `current.json`-scoped counts. This matches FACET-02's literal phrasing ("today/7d/30d... plus monthly-archive access") as two dimensions, not one unified pool.

3. **Sort order per facet:** `byFamily` — descending by count (matches every ranking table convention in this repo). `byRegion` — ascending by canonical region_id (1..16, numeric compare, not string compare), matching the `/rankings/` region-list convention (order stays stable across builds regardless of count fluctuation). `byMonth` — descending by yearMonth string (newest first), matching the existing `monthGroups` convention already live in both pages.

4. **Module shape:** One default export `computeNewsFacets(incidents: IncidentLike[], index: CommuneMeta[], archiveDir?: string): NewsFacetIndex` returning `{ byFamily, byRegion, byWindow, byMonth }`. Plain exported `interface`s (`NewsFacetIndex`, `FacetBucket`, `IncidentLike`, `WindowFacet`), no class — mirrors `data.ts`'s functional/memoized style (PATTERNS.md, RESEARCH.md "Alternatives Considered"). Archive-file reading (new I/O this phase introduces) lives inside `newsFacets.ts` itself, applying per-file `existsSync`/try-catch discipline (RESEARCH Pitfall 4) — `current.json` parsing stays owned by each page exactly as today; `computeNewsFacets` receives the already-parsed `incidents` array as a parameter, never does its own `current.json` I/O.

5. **Family key set:** Derived from `new Set(incidents.map(i => i.family).filter(Boolean))` — never from `Object.keys(FAMILY_LABELS_EN)` (which contains the phantom CEAD-only `homicidios` key that has zero news incidents). `FAMILY_LABELS_EN`/`FAMILY_LABELS_ES` from `familyDefs.ts` are imported and used **only** for display-label lookup on the keys actually observed in data (closes RESEARCH.md Pitfall 2).

6. **facets.mjs adopted as validator #16.** `all.mjs`'s `VALIDATORS` array and its header doc-comment (which currently enumerates 1–15) are both updated in this same plan so the suite is 16/16 by the time this plan's tasks are verified. No other document in this repo hardcodes "15 validators" as an assertion (STATE.md's "15/15" is a narrative status line, updated at phase close in Plan 02's final task, not a test assertion) — no other file needs changing for this renumbering.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `data/incidents/current.json` / `archive/*.json` -> `newsFacets.ts` | File-system input written by an upstream Python pipeline (RSS-sourced, LLM-classified); values like `cut`, `date`, `family` are structurally trusted (schema-validated upstream) but not guaranteed type-consistent (string vs number `cut`) or gap-free (missing archive months) |
| `facets.mjs` (standalone Node script) -> `data/` tree | Read-only file access at validate-time; script must never write to `data/` or `site/**` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-01 | Tampering | `newsFacets.ts` archive directory read | mitigate | Per-file `existsSync` + try/catch around `JSON.parse` for each `archive/*.json` — a malformed or partially-written (OneDrive torn-write risk) month file is skipped, not fatal, and never crashes the Astro build (Pitfall 4 discipline) |
| T-27-02 | Information Disclosure | `facets.mjs` FAIL messages | accept | Failure messages may echo a malformed CUT or family value from untrusted RSS-derived data into validator stdout (CI logs); acceptable — this is already-published news metadata, not a secret, and CI logs are not public in this repo's current setup |
| T-27-03 | Denial of Service | `readdirSync` on archive directory | mitigate | Filter matched filenames with a strict `/^\d{4}-\d{2}\.json$/` regex before opening any file — prevents accidentally trying to parse an unrelated or oversized file that lands in the same directory |
| T-27-04 | Tampering | `facets.mjs` writes | mitigate | Validator is read-only by construction (no `writeFileSync` call anywhere in the file) — code review checklist item; no facet artifact is ever written under `site/**` per FACET-06 |
</threat_model>
