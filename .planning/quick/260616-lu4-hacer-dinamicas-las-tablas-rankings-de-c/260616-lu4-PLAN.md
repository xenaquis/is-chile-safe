<objective>
Make the two ranking tables (region commune table + national crime-type table), in both EN and ES, dynamically sortable and year-selectable via progressive enhancement — pure vanilla JS in a single shared Astro component, zero new runtime deps, zero React, no SEO regression.

A small client script hydrates on top: clickable column headers that toggle asc/desc sort, and a year <select> that recomputes/reorders each row's displayed rate from per-row embedded data. <design_decisions>
<!-- Read these BEFORE implementing — they resolve the ambiguities flagged in the brief. -->

D-1 (national_rank is fixed, order is dynamic): The national_rank badge ("#12" / "—") shown in a row is the canonical server-side rank for the latest complete year and MUST NOT be recomputed when the user changes sort or year. Only (a) the visual ROW ORDER and (b) the displayed RATE value change client-side. Rationale: national_rank is a documented canonical statistic (CR-01 in the crime pages); recomputing it per-year in the client would silently diverge from the indexed value and the JSON-LD ItemList. The rank column header is therefore NOT sortable/relevant to reorder by — sort happens on rate (and name).

D-2 (low_population semantics preserved): low-pop rows always sort to the BOTTOM of the table as a separate group, keep the `*` marker and the `—` rank cell, in every sort direction and every year. Implement by partitioning rows into eligible vs low-pop, sorting each group, then concatenating eligible-first. This mirrors today's server-side `[...eligible, ...lowPop]` build.

D-3 (year selector excludes partial years): The <select> options are built ONLY from complete years (partial !== true). Default selected option = latest complete year (current behavior). 2026 (partial) is never offered. This replicates `latestCompleteYear` semantics exactly.

D-4 (single shared script): One component `RankingTableEnhancer.astro` carries the entire vanilla-JS module + the year-<select> markup. It is generic: it finds every `table[data-ranking-table]` on the page and wires it independently, reading config off the table's own data-* attributes (which rate column to mutate, locale for number formatting). Both table contexts include this one component. No per-page script duplication.

D-5 (rate column is the dynamic one): Each row embeds `data-rates='{"2024":123.4,...}'` — a compact JSON map of completeYear -> rate for THAT row's metric (region: total rate; crime: family/homicide rate). On year change, the script reads data-rates[selectedYear], rewrites the rate <td> text (locale-formatted), then re-sorts. Region table currently renders Math.round(rate); crime table renders 1-decimal — the enhancer reads a `data-rate-format` attribute ("round" | "1dp") off the table to match the server format exactly.

D-6 (accessibility): Sortable headers become <button> elements inside the <th>, with `aria-sort` on the <th> (none|ascending|descending) updated on toggle. The year control is a <label for> + <select id>. The whole controls strip is added by the enhancer (so JS-off users never see a non-functional control).
</design_decisions>
